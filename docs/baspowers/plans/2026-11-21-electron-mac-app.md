# Mac app on Electron Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: implement this plan task-by-task with the skill named in **Execution**. Steps use checkbox (`- [ ]`) syntax.

**Execution:** baspowers:subagent-driven-development (fifteen pull requests with separate review surfaces). Each is its own branch from `main` and gets its own task breakdown, written from its section here when it starts.

**Goal:** The Mac app is an Electron shell around the bundled web build, with the hidden title bar, Quick Capture, updates and notifications, and current Mac users are moved to it by one Sparkle update that asks first and deletes nothing.

**Architecture:** `electron/` holds a small main process and a typed preload bridge; the page loads from `capacitor://localhost/` (the origin of the iPhone app, which backends already accept) out of the `dist` inside the signed archive. Web code asks `src/app/lib/nativeShell.ts` what shell it runs in, and each `src/app/native/*.ts` module chooses the bridge or the Capacitor plugin inside. The Electron app ships as a separate beta app until the cutover, then takes the Catalyst app's name, bundle ID and DMG.

**Tech Stack:** Electron 45.4.1 (exact pin), electron-builder 26.18.0, electron-updater 6.8.11, esbuild, Swift (one helper, for the screenshot), TypeScript (strict), vitest, Playwright `_electron`, GitHub Actions (`macos-26`).

**Spec:** `docs/baspowers/specs/2026-11-21-electron-mac-app-design.md`. Read it first: the reasons, the security rules, the feature table, the migration and the rollback are there.

**Review state:** P1 to P5 (up to the signed beta) and the rules below are exact and get one more plan review. P6 to P14 are final in scope and size; a point marked **Decide in PR** is settled in that pull request's own review.

## Review Focus

- A request for `capacitor://localhost/../../etc/passwd`, `%2e%2e/`, an absolute path or another host must never read outside `dist`, and a route with dots (`/!abc:server.org/$event`) must get `index.html` (P2, `bundleProtocol.test.ts`).
- On the page that has the bridge, an inline script, an inline handler, a script added from a string, a remote script and `eval` must not run. A canvas must still run its scripts and report an escape, in a frame with an opaque origin and no bridge; a frame page opened as the main frame must not load, and no IPC call is served for a sender whose origin is not the app's (P2, P2b).
- No media URL holds an access token in the desktop app; main adds the `Authorization` header only to a first-hop `GET` that has none, from one of our windows' main frames, for that window's active account's homeserver media; never to a subframe, a canvas or a redirected hop, and it never changes a header the caller sent (P1, P2c). P2 opens nothing outside. From P3 on: a scripted `window.open`, `a.click()` or click on a marked button opens nothing, and the page has no function that opens a URL; a real click or middle click on a link opens the browser once; a misleading link opens nothing when the question is cancelled and exactly once when confirmed; a `javascript:` or `file:` URL, a media URL or one with an `access_token` is refused.
- The sign-in opener refuses any URL but the named homeserver's SSO endpoint with exactly the stored `redirectUrl`. The loopback listener delivers only a `GET` with its own `Host`, the stored path, and the stored query plus one `loginToken`; a wrong request first and the right one after it still signs in; a return that is late, repeated or for another homeserver signs nobody in (P3).
- A dialog or menu that overlaps the title bar strip must take clicks there, and saved bounds on an unplugged display must not open a window off screen (P2 `shell.spec.ts`; P4 `windowState.test.ts`).

The privileged page runs bundled scripts only. A `srcdoc` frame inherits its parent's policy, so canvases move, in the desktop app, to a bundled frame page with its own policy; the web and the phone keep `srcdoc`. Both land in one pull request, so no build has the policy without working canvases.

- [ ] Script policy: `electron/build.mjs` writes the sha256 of each inline script of each HTML file in the built `dist` (today `index.html:26` and `pdf-frame.html:32`); a file with an inline script that has no hash fails the build's check. `pageHeaders` takes the requested pathname for `framingHeaders()` (`scripts/frame-headers.mjs:29-40`), because after the fallback to `index.html` the file no longer says whether the route was `/connect` or `/invite`, and the resolved file's hashes for `scriptPolicy`; it joins the two into one `Content-Security-Policy` header (a second header of that name would replace the first in a `Response`); `X-Frame-Options` stays. The `<meta>` policies of `index.html` stay and narrow it further.
- [ ] `canvas-frame.html` holds one inline loader: it posts `canvas-frame-ready` to its parent with the target origin `capacitor://localhost`, takes the first message whose `source` is its parent and whose `origin` is `capacitor://localhost`, and replaces itself with it (`document.open`, `write`, `close`). Its header is `CANVAS_FRAME_POLICY`, whose `sandbox allow-scripts allow-forms` gives it an opaque origin even when a page embeds it without the attribute. Its script and style sources name `capacitor://localhost/<canvas library directory>/` (`canvasLibraries.ts:27-35`: `'self'` matches nothing in an opaque origin). `'canvas-frame.html'` joins `FRAME_PAGE_FILES`. The canvas document's own `<meta>` policy (`canvasDocument.ts:455,489`) still narrows it, and the wrapper still sets the inner frame's `srcdoc` (`canvasDocument.ts:517`).
- [ ] `useCanvasFrame`: outside the desktop app `{ srcDoc: doc, onLoad, generation: 0 }`, as today. In the desktop app `{ src: '/canvas-frame.html', onLoad: counted, generation }`. Two things make a new frame. A changed `doc`: a `srcdoc` frame shows it by itself, a fixed `src` would keep the old one, and `InlineCanvasFrame.tsx:139,312,338-341` changes `doc` (the remote-assets toggle) without changing a key; so `generation` counts the documents the hook was given and both callers add it to their iframe's `key` (`CanvasPanel.tsx:240`, `InlineCanvasFrame.tsx:139`). A restart: an escape remounts the iframe with the same `doc` (`InlineCanvasFrame.tsx:74-87`). So the handshake and the load count belong to the mounted iframe, not to the document: the hook posts the current `doc` once to each `contentWindow` that sends `canvas-frame-ready` (it must be the current frame's, with origin `'null'`), and `counted` swallows the first `load` of each iframe element and forwards every later one (`useCanvasHost.ts:449-454` calls a second `load` an escape, and this frame loads twice by design: the page, then `document.close()`). The host's own counter and the inline frame's count of escapes sit outside the keyed iframe and are untouched. The sandbox attribute, `allow` and `referrerPolicy` do not change.
