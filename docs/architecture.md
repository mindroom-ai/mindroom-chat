# Architecture

MindRoom Chat is a single-page React app that talks to a Matrix homeserver through `matrix-js-sdk`, and to a MindRoom backend's HTTP API for the features that need one (agent computers, Connections, Local MindRoom pairing). This page covers how it starts, where the code lives and the rules for placing it, the two kinds of code in the repository, and how it reads the event formats MindRoom agents send.

## Stack

React 18.2, TypeScript 5.4 and Vite 5.4; vanilla-extract for styles (`*.css.ts`) and the folds component library; jotai for UI state, TanStack Query for server reads, React Router 6, Slate for the composer, i18next for translations; `matrix-js-sdk` 41.7 with its Rust crypto (`@matrix-org/matrix-sdk-crypto-wasm`); `livekit-client` for calls; Workbox for the service worker; Capacitor 8 for the iOS and Android shells. Versions are pinned in `package.json`, and `patches/` holds patch-package fixes to some of them (`matrix-js-sdk`, `folds`, `i18next` and others), applied by `npm ci`.

## How the app starts

1. `index.html` loads `runtime-config.js` (`src/boot/runtimeConfig.ts`: base path, service worker switch, sign-in recovery settings) and `authentication-recovery.js` (`src/boot/authenticationRecovery.ts`), then the module `src/index.tsx`.
2. `src/index.tsx` starts diagnostics, applies the stored theme, loads i18n, registers the service worker (`src/sw/sw.ts`, which serves the cached app shell, precaches only what a signed-in start needs (`scripts/precache-plan.mjs`), keeps the build's other files on first use (`src/sw/swRuntimeAssets.ts`) and the language catalogs with their overlays (`src/sw/swLanguageFiles.ts`), and fetches authenticated media) unless it is switched off, watches for parts that cannot load after a deployment (`src/app/config/appUpdate.ts`), and renders `App`, whose root error boundary (`AppErrorBoundary`) shows a failed screen with Reload.
3. `src/app/shell/App.tsx` sets up jotai, the theme and TanStack Query, loads `config.json` (`src/app/config/ClientConfigLoader.tsx`; see `docs/configuration.md`), and creates the router (`src/app/shell/Router.tsx`).
4. Sign-in pages live under `src/app/account/auth/`. Every signed-in route renders `ClientRoot` (`src/app/shell/ClientRoot.tsx`), which builds the active account's `MatrixClient` (`src/app/account/lifecycle/initMatrix.ts`: IndexedDB stores, Rust crypto, sync), shows the startup screen until the first sync, and then the shell with the icon rail.
5. Accounts are kept in a session registry (`src/app/matrix/session/sessions.ts`), each with its own stores, so several accounts can be signed in and switched.

## Placement and naming

Where a file goes, first match wins:

1. **Domain.** A file goes to the domain of the screen or concept it serves. A file several domains use goes to the lowest domain all of them may import (see [Layers](#layers)), and its own imports must not climb above it. If a file would have to import a higher domain, move the shared part down; never move the import up.
2. **Component:** `<domain>/<Name>.tsx`, with its styles in `<Name>.css.ts` beside it. A sub-folder only for a sub-feature of three or more source files.
3. **Hook:** with its domain. A hook that only wraps React or the DOM goes in `lib/hooks/`, one that only reads Matrix data in `matrix/hooks/`.
4. **Atom:** with the domain that owns the state. Client-derived global state goes in `matrix/state/`, user preferences in `preferences/`, atoms that only open a dialog in `navigation/`.
5. **Pure helper:** domain logic in its domain, Matrix event logic in `matrix/`, `io.mindroom.*` content formats in `matrix/protocol/`, text formatting in `rich-text/`, helpers with no app knowledge in `lib/`.
6. **Tests:** `X.test.ts(x)` or `X.<aspect>.test.ts(x)` beside `X`; tests of several modules in `<domain>/__tests__/`; shared helpers in `src/test/`, one domain's helpers in its `__tests__/` or `test-utils/`; fixtures in `<domain>/__fixtures__/`.
7. **Settings pages:** a page about one domain's objects lives in that domain and is built from `ui/settings/`; pages for app-wide preferences live in `settings/pages/`.
8. **Route pages:** in the domain that owns the screen (`threads/page/`, `canvas/page/`, `rooms/explore/`, `notifications/inbox/`, `account/auth/`, `room/RoomRoute.tsx`). `shell/Router.tsx` maps `routes/paths.ts` to the lazy modules of `shell/clientPages.tsx`; there is no `pages/` folder.
9. **e2e:** `e2e/<domain>/<name>.spec.ts`, and `<name>.live.spec.ts` for long specs against the live homeserver.

No barrel files: import a name from the module that declares it. The two `index.ts` files that stay, `event-store/engine/index.ts` and `event-store/cache/db/index.ts`, are the public surfaces of the sync engine and the cache database, which their architecture tests check. The client SDK (`src/client-sdk/`) is a third exception: its modules re-export the app for client plugins, and the app never imports the SDK.

Naming:

- Drop `Mindroom` and `MindRoom` where they only marked the code as ours rather than upstream (`room/Room.tsx`, `messages/Message.tsx`). Keep product and protocol names: Local MindRoom (`local-mindroom/`), the `MINDROOM_*` event constants, `isMindroomAgent*`, `io.mindroom.*`, storage keys, persisted IndexedDB names, the `window.__MINDROOM_*` globals that e2e specs read, and the i18n namespace `mindroomUi`.
- Name by content: `renderAgentMessageContent.tsx`, `agentCommandQuery.ts`, `prefetchSettings.ts`.
- A component file is named after its export (PascalCase), a hook `useX.ts`, everything else camelCase. A file and its main export are renamed together.
- No two modules in one folder whose names differ only in case: the iOS app is built on a case-insensitive file system.

## Layers

A domain imports only domains in a strictly lower layer. Runtime, type-only and dynamic imports all count; tests are exempt; inside a domain, sub-folders import each other freely.

| layer | domains |
|---|---|
| 0 | `lib`, `src/boot`, `src/types` |
| 1 | `config`, `i18n`, `preferences`, `routes`, `shortcuts`, `src/sw` |
| 2 | `diagnostics`, `native`, `ui` |
| 3 | `matrix`, `theme` |
| 4 | `avatars`, `models`, `navigation`, `plugins`, `rich-text`, `ui-actions` |
| 5 | `computer`, `emoji`, `event-store` |
| 6 | `approvals`, `bug-reports`, `calls`, `connections`, `editor` |
| 7 | `background-jobs`, `members`, `messages` |
| 8 | `canvas`, `composer`, `notifications`, `schedules`, `search` |
| 9 | `rooms`, `threads` |
| 10 | `account`, `spaces`, `timeline` |
| 11 | `command-palette`, `local-mindroom`, `room` |
| 12 | `settings` |
| 13 | `sidebar` |
| 14 | `shell` |
| 15 | `src/index.tsx`, `src/client-sdk` |

`just lint` enforces it: `.eslintrc.cjs` builds `import/no-restricted-paths` zones from the `LAYERS` list, and every violation names its domain and layer and points here. The resolver setting beside it lets the rule see extensionless TypeScript imports; without it the rule would skip them silently. `src/test/layering.test.ts` lints probe imports under made-up paths and fails when the zones go silent, when a folder of `src/app` has no layer, or when a zone names a folder that does not exist. A new domain needs a place in `LAYERS`.

Limits:

- Inline type imports (`typeof import('...')`) are not checked by the rule. The one cross-domain use, `shell/Router.tsx` to `room/Room`, points downward.
- File-level cycles are checked separately: `threads/__tests__/featureOwnership.architecture.test.ts` requires the runtime import graph of `src/app` to be acyclic, apart from one listed cycle, `emoji/emojiData.ts` and `emoji/emoji.ts` (a lazy `import()` and the handover of the emoji tables back). Remove the allowance when that handshake goes.

## Client plugins

A build can add code from outside this repository: `MINDROOM_CLIENT_PLUGINS` names plugin directories ([`configuration.md`](configuration.md#build-time-variables)). Each has its own installed `node_modules`, so this repository's `package.json` and lockfile stay as they are, and a `package.json` that declares the plugin:

```json
{
  "name": "my-plugin",
  "version": "1.0.0",
  "mindroomClientPlugin": { "id": "my-plugin", "apiVersion": 6, "entry": "./src/index.tsx" }
}
```

- `scripts/client-plugins.mjs` checks each declaration, failing the build on one it cannot use, and replaces `src/app/plugins/pluginEntries.ts`, which lists no plugins, with a module that imports each entry. Without plugins none of their code ships.
- A plugin imports the app only through the client SDK, `@mindroom/client-sdk/<subpath>`; the build resolves each subpath that `CLIENT_SDK_ALIAS` in `scripts/client-plugins.mjs` lists to its module in `src/client-sdk/`, and `tsconfig.json` maps `@mindroom/client-sdk/*` to `src/client-sdk/` for this repository's type checks. Each subpath is a module of its own, so a plugin's entry, which loads with the app, binds only the subpaths it imports. `core` has the plugin types (`ClientPlugin`, `MessageRenderer`, `PluginEvent`, `PluginPage`, `PluginPageProps`), `usePluginConfig`, `usePluginStorage`, `usePluginTranslation`, `getPluginTranslation`, `useRoomSidePanel`, `usePanelFrame`, `pluginRoutePath`, `usePluginRouteHref`, `pluginPublicUrl`, `reloadForNewVersion()`, which reloads the page into the newest version the server has, as the app's own update notice does, also when the page has not noticed that version yet, and `commandUsage()`, the refusal a slash command's `run` throws to show its usage. `matrix` has the signed-in account's Matrix data, as the app reads it: `useMatrixClient()`, the account's `MatrixClient`; `useRoomMembers(client, roomId)`, the room's members (matrix-js-sdk's `RoomMember`, with `membership`, display `name` and avatar), rendered again on each change of a member's membership, name or power level, the full list loaded in the background; `hasActiveMindroomAgent(members)`, the app's own test of a room with an agent: whether a member who has joined or is invited has a MindRoom agent's user ID, and `isMindroomAgentUserId(userId)`, its test of one user ID: whose localpart starts with `mindroom_`, in any letter case, on any homeserver, so both name agents but prove none; `useRoomPermissions(room)`, what the room lets a user do, as the app answers it: `event(eventType, userId)` and `stateEvent(eventType, userId)` for sending events, `action(action, userId)` for `invite`, `kick`, `ban` and `redact`, and `notification(key, userId)` for a notification such as `room` (`@room`), from the room's power levels and, from room version 12, its creators, who outrank every level, rendered again when either changes; `getRoomPermissions(room)`, that answer read once from the room's current state, for code that is no component, such as a slash command's `run` or a room menu entry's `shows` and `run`; read it again for a later answer; `getMemberDisplayName(room, userId)`, the name the app's timeline and member list show for a member of the room, with the user ID after it (isolated, between U+2066 and U+2069) when another member shows a name that reads the same (a member without a name shows as their user ID's localpart) or the name looks like a user ID or holds hidden characters, which are left out, and for one who left without a name the name they last had, or undefined for someone without a name of their own, whom the app names by their user ID's localpart, or whom the room does not know, decided from the members the client has loaded (in a room whose member list has not loaded yet, a copied name may show without the user ID); and `useMediaAuthentication()`, whether the app asks the homeserver's authenticated media endpoints (Matrix 1.11), which it does once the homeserver has them and a service worker that adds the access token controls the page, or in the native app, rendered again when a service worker takes control, for `mxcUrlToHttp(client, mxcUrl, useAuthentication, width?, height?, method?)`, the HTTP URL of an `mxc://` URI as the app's own media use it, a thumbnail when a size is given (`method` `crop` or `scale`), or null; in the native app without a service worker it carries the account's access token, so it is for the account's own requests only. `room` takes the user to rooms and threads, creates sub-rooms and names the rooms a room is a sub-room of, and shows a person's profile card: `useRoomNavigate()` gives `navigateRoom(roomId, options?)`, which opens a room where the app opens it (in its space, in Direct, or in Home), and `navigateRoomThread(roomId, threadId, options?)`, which opens a thread whose back button returns to the page it was opened from. `options` is `{ eventId?, replace? }`: `eventId` opens the room, or the thread, at that event, scrolled to and marked as the app's own message links open one, and `replace: true` puts the room or the thread in place of the current page in the history, so Back skips that page, and the back button of a thread opened so leads to the page before it, or to the room when the app has shown none. Only those two count, so a callback's extra argument there (an index, a click event) opens the room or the thread itself, as a new page. And `useRoomHref(roomId, threadId?)` is the `href` of the room or the thread at that path, with the base path or the hash router the app uses. `createSubRoom(parent, { name })` creates a sub-room of the room `parent` called `name`, as the room menu's New Sub-room does, and resolves to its room ID: listed under `parent`, open only to its members, and encrypted and federated as `createRoom` in `config.json` says when it is called, with no option for either. The room menu offers New Sub-room in chat rooms only, not in spaces or direct chats, and `offersSubRooms(room)` says whether it offers it in `room`; `createSubRoom` takes any room it may list rooms in, so a plugin asks `offersSubRooms` to offer it where the menu does. `createSubRoom` is no hook, so a slash command's or a room menu entry's `run` calls it as well as a component; it refuses, creating nothing, a blank name, a parent where the signed-in user may not list rooms, and a call while the app provides no configuration (in a plugin's test, while nothing `renderPluginComponent` rendered is mounted). When the homeserver refuses to list the new room under `parent`, it leaves and forgets the room, if the homeserver lets it, and rejects with that refusal. It resolves once the server has created the room, before sync has it, and does not open it; `navigateRoom` does. `useParentRooms(room)` gives the chat rooms the client has that list `room` as a sub-room, spaces left out, as the room menu's Remove from lists them, rendered again when a link to `room` changes; `getParentRooms(room)` reads the same once, as `offersSubRooms` does, for a slash command's or a room menu entry's `run`. In a plugin's test, where the app follows no rooms, `useParentRooms` gives none and `offersSubRooms` takes no room for a direct chat. `useOpenUserProfile()` gives a function `(roomId, userId, anchor, side?)` that opens the profile card of the person `userId` in the room `roomId` as a mention pill opens it: floating at `anchor`, an element's rectangle (`getBoundingClientRect()`), on its `side` (`Top`, `Right`, `Bottom` or `Left`, where `Left` and `Right` follow the reading order; below it unless given), until Escape or a click outside closes it; for a room the client does not have, it opens nothing, also once sync brings the room. `UserProfileCard` (`{ room, userId, onDone }`) is that card itself, for a plugin's own surface such as its side panel: the person's avatar, name and ID, power tag, shared rooms, server, Message, moderation and blocking, as the floating card shows them; `onDone` runs once the card has done its job: before it opens a direct chat, a shared room or the settings, and when a call starts. Like the floating card, it starts afresh when `room` or `userId` changes, so what was begun for one person, such as a ban and its reason, never goes to the next. `server` reaches the room's MindRoom server, for a plugin whose MindRoom plugin serves routes under `/api/plugins/<name>/` (MindRoom's `docs/plugins.md`, "HTTP routes"): `useMindroomServer(roomId)` gives that server by the rule call transcripts use (the one the room's agents published while the homeserver binds sign-in tokens to it, else `mindroom.computers.apiUrl` from `config.json`), or undefined in a room without a MindRoom agent or without either. It has the server's `origin`; `request(path, init?)`, which sends a request to that path as the signed-in user, with their client session as bearer and no cookies, and resolves with the answer's JSON, undefined for an empty answer, or rejects with `MindroomServerError` (its `status`, 0 without an answer or for one that is not JSON, and the parsed `body`), and rejects with a `TypeError` for a path that leads to another origin before sending anything; `send(path, init?)`, which sends as `request` does, never from the HTTP cache, and resolves with the answer's `Response` whatever its type or status, such as an image a route serves, and rejects as `request` does without an answer, when the sign-in fails or for another origin; `openSocket(path)`, which resolves with a `WebSocket` (`wss:`, or `ws:` for an `http:` server) that offers the session as `mindroom-session` and `mindroom-session.<token>`, as MindRoom's `client_stream` takes it, and rejects as `request` does when the sign-in fails; and `token({ signal?, refused? })`, the session's token for a request `send` cannot make, such as an upload that reports its progress through `XMLHttpRequest` with `Authorization: Bearer <token>`, asked for anew for each request and never kept: it signs in when there is no session or it is about to run out, and after a 401 the plugin asks again with `refused`, the token the server refused, which signs in again, and sends once more. The app and every plugin share one session per account and server, since MindRoom keeps eight per user and a ninth sign-in ends the oldest (`src/app/computer/clientSessions.ts`): it is renewed a minute before it runs out, a 401 signs in again and sends once more (so a plugin's route refuses with 403, never 401, for reasons of its own), and sign-out ends every session the page may still hold there (`DELETE /api/client-sessions`), once a call transcribed on this device left with it (3 seconds at most). Reconnecting is the plugin's: the server closes a socket with 4401 once its session ends, after which the next `openSocket` signs in again, with 1012 when the plugin reloads, with 1008 once the user left the room and with 1013 while membership is unavailable; a handshake it refused shows only as a socket that closes before it opens, so the next `openSocket` first asks `GET /api/plugins` whether the session lives and signs in again only on a 401, and a refused origin or membership never ends the user's other sessions. `ui` has the app's own components, with the app's props, so a plugin's menus, dialogs, pop-outs and rows look like the app's, in its theme: the glass `Menu`, `Dialog`, `Header` and `IconButton`; `MenuEntry` and `MenuGroup`, the room menu's rows and the groups they come in; `NavItem`, `NavButton` and `NavItemContent`, the sidebar's rows; `PopOut`, folds' pop-out placed in reading order, so on a right-to-left page its `position` `Left` and `Right` trade places, and so do its `align` `Start` and `End` along the anchor's top or bottom; and `IconTooltip`, an icon button's tooltip, placed so too. For text, such as an agent's, that a plugin shows as the app does, `ui` also has `useMarkdownHtml(markdown)`, the HTML of `markdown` as the app renders an agent's reply while it streams: sanitized, with the link schemes `messageRendering.additionalAllowedUriSchemes` in `config.json` adds; undefined until the app's Markdown renderer has loaded, which it starts loading, and rendered again once it has; `sanitizeHtml(html)`, `html` with only what the app keeps of a message's HTML, under the app's default policy, which a plugin cannot loosen: no script, event handler or `javascript:` link, and images only from `mxc://` sources, which `mxcUrlToHttp` turns into ones a browser loads; and `replaceMatrixUserIdsWithDisplayNames(room, text)`, `text` with the Matrix user ID of each member of `room` replaced by the name the app shows for them there, also before trailing punctuation, as thread previews show an agent's message, which names people by their IDs; other IDs stay. The names it puts in are plain text: in Markdown given to `useMarkdownHtml` afterwards, a name's own Markdown takes effect, and IDs in code or in a link's target are replaced too. The plugin puts the HTML into its own element (React's `dangerouslySetInnerHTML`), without what the app adds as it draws a message, such as: links and mentions in it are plain links, without the app's pills or link handling; math stays as its `$` text, which the app typesets; a spoiler (`data-mx-spoiler`) shows, where the app hides it until a click; and direction controls (such as U+202E, which reverses what follows) stay as they are, as in any text a plugin renders, where the app shows them as code points (`<U+202E>`). The app's unit test setup draws `Menu`, `Dialog`, `Header` and `IconButton` as folds' plain components, so in a plugin's tests a menu's rows are found by their text, not as `menuitem`s. `testing` is for a plugin's tests only: only the unit tests resolve it (`vitest.config.ts`), so the build fails on code that ships and imports it. `renderPluginComponent(ui, { id, plugin, config, language, client, frame })` renders a plugin's components into the document (the test needs `// @vitest-environment jsdom`) with `config` as the plugin's `config.json` section, its strings in `language`, English unless named, `client` as the account's client (such as one from matrix-js-sdk's `createClient({ baseUrl, userId })` whose store holds the test's rooms; unless given, a stand-in that has its user ID, builds media URLs for `mxcUrlToHttp` on `https://example.org` and knows no room), `frame` as the side panel frame `usePanelFrame` returns, as the app gives it to a panel with `frame: 'own'` (unless given, none), and its storage for that account, signed in, and unmounts them after each test; what they store stays for the rest of the test file. the app's floating profile card is not rendered there, so what `useOpenUserProfile` opens does not show; one that uses `useMindroomServer` needs a `client` from `createClient`, whose homeserver the hook asks through `fetch` whether it binds sign-in tokens, so the test stubs `fetch`. `apiVersion` is the SDK version the plugin needs: the build refuses a plugin that needs a newer one than it provides (`CLIENT_PLUGIN_API_VERSION` in `scripts/client-plugins.mjs`, now 34; - The app shares its React, React DOM, matrix-js-sdk, jotai, TanStack Query, React Router, i18next and react-i18next, folds, focus-trap, focus-trap-react, dayjs and react-aria, with the packages some of them are built on (scheduler, @tanstack/query-core, @remix-run/router), with every plugin (`SHARED_PACKAGES` in `scripts/client-plugins.mjs`): in a build and in the dev server, a plugin's imports of them, and those of the packages it installed, resolve as the app's own imports do, to the app's copies in the app's versions, so the state each keeps is one (the Matrix SDK's classes, query caches, atom stores, the router, translations, focus traps, the date locale, the scroll lock, overlay stack and focus scopes of dialogs and menus); a CommonJS package's `require` of one gets the module the app imports too. A build needs none of them installed in the plugin's directory, wherever it is, and does not use a copy installed there (for the plugin's tests, or for one of its packages); an import the app's copy cannot resolve, such as a file only a newer version has, fails the build. A plugin directory inside another one belongs to the inner plugin, and the app's own directory inside a plugin directory to the app. The dev server pre-bundles the packages a plugin installed without plugin hooks; there an esbuild plugin in `scripts/client-plugins.mjs` resolves their imports and requires of the shared packages. Not redirected: packages linked in from outside the plugin's directory (`npm link`, `file:`), which the notices and the bundle report below do not count as the plugin's either, a plugin's `?worker` bundles in a build, and its `.css.ts` style files, which vanilla-extract compiles on its own. A plugin lists the ones it imports under `peerDependencies`, never `dependencies`: the build fails, naming the plugin and the package, on one under `dependencies`, and on a copy of one the plugin bundles under another name (an npm alias). A plugin uses the app's `QueryClient` (`useQueryClient()`, or `useQuery` without a client of its own), never one it creates: the app keeps one per signed-in account.
- Every other import of a plugin, the client SDK's aside, resolves in its own directory, so a package the plugin installed comes from its `node_modules`, even one the app bundles too; the build's check for two copies of one package version (`scripts/package-copies.mjs`) leaves those out. The third-party notices the build ships, which anyone can read, list the production packages of each plugin's `package-lock.json` that are installed in its directory, with their names, licenses and repositories, and `just license-check` checks every package installed there, both for the plugins `MINDROOM_CLIENT_PLUGINS` lists. With the same variable, `scripts/perf/bundle-report.mjs` (`just bundle-report`) lists the minified and gzip size of the JavaScript each plugin adds, its packages included, from the source maps of `npx vite build --sourcemap`.
- A declaration may add `build`, a path in the plugin's directory to an ES module whose default export is a Vite plugin or an array of them, for the transforms the plugin's own modules need, such as scoping a style sheet one of its packages ships to the plugin's own elements, or marking its modules free of side effects. `clientPlugins` in `scripts/client-plugins.mjs` imports it and adds its plugins to the build, before its own, with each hook kept to the plugin's modules, those of the packages it installed included, as above: `transform` and `load` run only for them, the modules its `resolveId` makes up included, whose ids start with `\0`, its id and a colon (Vite's virtual modules, named for the plugin, such as `\0my-plugin:settings`), and `resolveId` only for their imports, while `name`, `enforce` and `apply` mean what they mean in Vite, so a plugin's hooks see none of the app's modules or another plugin's; any other hook or property fails the build, naming the plugin and the hook. A made-up module's imports resolve from the app's directory, as Vite resolves a virtual module's, unless the plugin's `resolveId` takes them. A `resolveId` with `enforce: 'pre'` sees the plugin's imports of the packages the app shares before they resolve to the app's copies, so it can put a module of the plugin's own in place of one for a package it installed, such as a module that exports only the names a big CommonJS bundle reads; that module imports the package by its name, and the plugin's `resolveId` passes that import on (returns null for it), so it resolves to the app's copy. The hooks run in the build, and in the dev server for the files it serves itself unless `apply: 'build'` keeps them out; not in the unit tests, nor where the dev server pre-bundles the packages a plugin installed, nor in the bundles of `?worker` imports, which take only `worker.plugins`. A build module is code the build runs, as an entry is code the browser runs: the build trusts the directories `MINDROOM_CLIENT_PLUGINS` lists.
- An entry's default export is a `ClientPlugin` (`src/app/plugins/registry.ts`): a list per kind of contribution, its strings, and an optional `forgetAccount` (account storage, below). `registeredPlugins` freezes them, in the listed order, when its module loads, and `src/index.tsx` loads it before the app routes. A plugin's module runs then, before `config.json` has loaded, so a plugin reads its settings (`plugins.<id>`) only while it renders, with `usePluginConfig(id)` (`src/app/plugins/pluginConfig.ts`).
- Message renderers (`src/app/plugins/messageRenderers.ts`) are the first kind: `{ match, Component, trust? }`. `RenderMessageContent` asks them before its own renderers, wherever it renders a message body: timelines, pins, the inbox, and search results short enough to show whole. `match(event)` is pure and synchronous, and sees the content the app renders the message from, latest edit included; `Component` renders it. Only a MindRoom agent on the viewer's homeserver may send the messages a renderer takes, or with `trust: 'server'` anyone on that homeserver. A `match` that throws counts as no match. A `Component` that throws shows the app's own rendering instead, until the message's content changes (as a reply streams in) or another renderer takes it, and the failure is logged and reported with `[plugin <id>@<version>]`.
- Side panels (`src/app/plugins/sidePanels.ts`) are the second kind: `{ id, label, icon?, placement?, Component, remember?, opensOverMembers?, frame? }`. Each is one more of the room's side panels, beside the computer, a canvas, the call, its live transcript and the members, under their rule (`src/app/ui/panels/roomPanels.ts`): one shows at a time, and opening one closes the others, except that the members stay open behind the call or its live transcript. Its `label` names it in the app's language when it is the key of one of the plugin's strings (`translations`, below), and exactly as given otherwise, such as text with `.` or `:` (which names no other namespace), a template like `$t(…)`, or the key of a group of strings. Its toggle in the room header, named by its `label` and drawn with its `icon` (a folds icon such as `Icons.Star`, a bulb unless given), shows and hides it, where `placement` puts it: `auto` and `menu`, the default, as they put a header action (below), and `row` in the header's row on every screen, phones included. The toggle is pressed, its button tinted and its menu entry checked, while the room shows the panel and the panel is not folded to its tab; choosing it then closes the panel, and choosing it while the panel is folded unfolds it with what it shows. The panel opens in the room it was opened in, as wide as the call panel and resizable (over the room on phones), with the label as its title and a Close button (unless it draws its own frame, below), and `Component` gets the room's id (`roomId`) and a `request` (below). Like the computer, a canvas and the call, it has the room's frame (`src/app/ui/panels/PanelFrame.tsx`, drawn by `ResizablePanel`), with no code of its own: a 40 px strip at the start of its box, which the panel's smallest width grows by, whose Fill puts it across the room in the conversation's place, and whose Fold leaves only a tab with its `label` at the room's edge, beside the conversation at full width, until the tab brings it back. While the room's page shows, each room keeps the layout of each of its panels as long as the panel stays open; a panel opens beside the conversation, and one asked for again while it fills the room stays so; each canvas shown, though, opens beside the conversation, or across the room from the Canvases page. The computer's and a canvas's own Expand fill the room as Fill does. Filling the room, or covering the conversation on a phone, a panel keeps the conversation under it as it was (its draft, a voice message being recorded, the reader's place), out of reach and out of sight as under a conversation cover (below): it takes no focus, sends no read receipt or typing notice, a message that arrives notifies as for a room not on screen, the composer's popovers (emoji board, autocomplete, model picker, menu) close, and neither an edge swipe nor the room's shortcuts for Members and resolving the thread act on it. Phones show no frame, as a panel there covers the conversation already, and the members have none: their header button shows and hides them. A panel with `frame: 'own'` draws its frame itself, such as a card with its own Fill and Hide: the room draws no title, Close, splitter or strip for it and gives it no box, so its `Component` takes its own width, and it opens and closes at once, without the frame's motion. `usePanelFrame()` gives a side panel's `Component` its frame, `{ label, layout, setLayout }`: `layout` is `beside`, `filled` or `folded`, and `setLayout` changes it as the frame's Fill, Fold and tab do, kept per room as above. The frame keeps its identity while the layout stays, and one the panel got in another room changes nothing in the room shown. A panel the room frames has it beside the conversation only, undefined on phones; one with `frame: 'own'` has it on phones too. Filling the room, such a panel takes the conversation's place as any does; folded, it covers nothing, on phones too, so the conversation lays out as with no panel beside what the `Component` still draws, such as its own tab at the room's edge. Over the conversation on a phone it also hides the room header, and with it the panel's toggle, so its `Component` offers a way out of its own: Hide, which shows the conversation beside its tab, or a Close that calls `close()` of `useRoomSidePanel` (below). While its `Component` loads its code, and if it throws, the room draws the panel's title and Close around it (below), so it can still be closed. A `Component` that throws shows "This panel stopped working." in the panel, which can still be closed, until it gets another `request`, and the failure is logged and reported with `[plugin <id>@<version>]`. A plugin's code opens its panels too: `useRoomSidePanel(id, panelId)` gives a component rendered in a room's page, such as a message renderer's card in the timeline, `{ isOpen, open, openBesideThread, close }` for the panel `panelId` of plugin `id` in that room, and undefined elsewhere (the inbox, the search page). `open(request)` opens the panel as its toggle does, under the same rule, or keeps it open and unfolds it, and hands `Component` `request`, which each `open` replaces; its toggle opens it with no request. `close()` closes it if it shows, and `isOpen` says whether it shows. `open` and `close` keep their identity while the room shows. A plugin opens its panel in answer to something the person does, such as a click, never as its component mounts: the conversation's components, a message renderer's cards among them, mount again whenever it shows another thread or view, so opening there takes the side panel back each time. The one exception is `openBesideThread(threadId, request)`, which a renderer of a thread's root message may call from an effect that depends on it, with its event's ID: it takes a new identity whenever the room shows another thread or its own timeline, so the effect asks again then, also in a card that stays mounted as its thread opens. Only the first call since the room began to show that thread counts, so a card that mounts again does not open a panel the person closed, and once another thread or the room's own timeline has shown, the thread's next call counts again. That call does something only while the room shows that thread and not on a phone: it opens the panel with `request`, beside the conversation, when no other side panel shows, or only the members list and the panel has `opensOverMembers: true`, which closes the list, and when the panel itself shows, it hands it the request and leaves it folded or filling the room. Otherwise it does nothing. A panel with `remember: true` stays open in each room it opened in, for the signed-in account, until it closes there (its Close, its toggle, another panel's opening in that room): after a reload, or a switch to another room and back, it opens again with its `request` when the room shows, unless another of the room's panels is open then (the members over the page, on phones or in a narrow room, do not count: the navigation puts them away). With `opensOverMembers: true` the members beside the conversation do not count either: the panel opens again in their place, and they close, as when the person opens the panel. The app keeps it in this browser, with the request as JSON, beside the account's plugin storage (`mindroom.plugin:<encoded user ID>/:side-panel/<encoded room ID>`, `src/app/room/usePluginPanel.ts`), so other accounts never see it and the app deletes it with the account's plugin storage (below). The request should therefore hold only what the panel needs to open again, never secrets or message text. Such a panel's `request` is a value JSON holds: when the panel opens again as its room shows, it comes back as `JSON.parse` reads it, and one `JSON.stringify` refuses (a `BigInt`, a cycle) makes `open` throw once the panel shows it, before the room remembers it.
- A plugin's strings (`translations` in `src/app/plugins/pluginTranslations.ts`): `en`, its English strings, which ship with its code, and `load(language)`, which resolves to the strings of another of the app's languages, such as `(await import('./locales/de.json')).default`, or to none; `language` is the code of the app's language, such as `de` or `zh-TW` (`src/app/i18n/i18nLanguages.ts`). The registry adds them as the i18n namespace `plugin.<id>` (`registerNamespace`, `src/app/i18n/i18n.ts`); a language without strings, or whose `load` fails, shows English, and a change of language waits until `load` settles. A component translates with `usePluginTranslation(id)`, whose `t` takes the keys of those strings (`a.b` for nesting) and i18next's options, and renders again in the app's language when it changes, and once strings that were still loading arrive; code outside React uses `getPluginTranslation(id)`, whose `t` translates into the language in use when called. A plugin's module runs once, before the strings of the language in use have loaded, and the language can change later, so it translates when its text shows, never when the module loads.
- The room header slot (`roomHeaderSlot`) is the third kind: components that get the open room (`room`, matrix-js-sdk's `Room`) and render under the room header, or render nothing, such as a banner about the room's state. They also get `headerRef`, a React ref to the header's element, which holds the header's row (the room's name and its buttons) and the slot, so a plugin can take something dragged from its side panel anywhere on the header: it reads the element's box for a drag it drives with the pointer, or listens to its drag events (`dragenter` and `dragover`, cancelled for its own drag type, and `drop`), and removes its listeners as it unmounts; it never changes the element. React sets the ref after the slot's components run their layout effects, so a component reads it in `useEffect` or in an event handler. The composer's file drop covers the header too but takes only drags that carry files, so a drag of the plugin's own type reaches the plugin untouched. `src/app/room/RoomHeaderSlot.tsx` shows them in build order inside the floating header, across the conversation column, on the header's own frosted surface (the slot adds no background of its own): the conversation's top inset grows with them, and it scrolls under them as under the header; where a short screen hides the header, it hides them too. Each mounts afresh in every room and renders again whenever the room view does, so one that shows the room's state listens to the room's events itself. One that throws shows nothing there, and the failure is logged and reported with `[plugin <id>@<version>]`.
- Header actions (`src/app/plugins/headerActions.ts`) are the fourth kind: `{ id, label, icon, placement?, run }`. Each is one of the room header's actions (`src/app/room/roomHeaderActions.tsx`), which the core ones are too: `placement` puts it in the room menu (`menu`, the default) or in the header's row of buttons, except on phones, where it goes in the room menu (`auto`); the room menu offers, in the row's order, every action its row leaves out. `label` is a key of the plugin's strings, shown in the app's language as the button's tooltip and name or as the entry's text; `icon` is drawn as folds draws its icons (`Icons.Star`); `run({ roomId, threadId })` runs it in the open room, and in the thread open there once the server has its root. A `run` that throws, or whose promise rejects, is logged with `[plugin <id>@<version>]`.
- Account storage (`src/app/plugins/pluginStorage.ts`): `usePluginStorage(id)` gives a plugin's components strings by key (`getItem`, `setItem`, `removeItem`) for the signed-in account, in localStorage under `mindroom.plugin:<encoded user ID>/<id>/`, so no account reads what another stored. When this browser deletes an account's local data (Logout, Remove from Device, a logout the homeserver reports, deactivation) and no other login of the same user ID stays, the app deletes every plugin's storage for that account and calls each plugin's `forgetAccount(userId)`, an optional function of its `ClientPlugin`, for what the plugin keeps elsewhere (its own IndexedDB database, say; the account's components are still mounted then, in this tab and maybe others, so a plugin closes its connections when they get `versionchange`, or the deletion waits). It waits for the promise `forgetAccount` returns, five seconds at most, before the page reloads; one that throws or rejects is logged with the plugin's tag. `setItem` stores nothing while no login of the account is left in this browser (it returns false), so a component that saves as it unmounts, in this tab or another, puts nothing back. As the app starts, it also deletes the plugin storage of every account without a stored login, which catches a value another tab wrote past that check while the account signed out (the sign-out's reload starts the app); it keeps all of it while the stored account list holds anything this version cannot read. Switching accounts and Clear Cache keep the storage, and `forgetAccount` runs whether `config.json` enables the plugin or not, but not in a page load with `?plugins=off`.
- Pages (`src/app/plugins/pluginPages.tsx`) are `{ path, Component, fillsWindow? }`. A plugin's pages live under `/p/<id>/` (`PLUGIN_ROOT_PATH` and `PLUGIN_PAGE_PATH`, one route for every plugin): `path` is a React Router path under that root (`''`, `items/:itemId`), matched and ranked as React Router matches routes, and `Component` gets its parameters as `params`. A page keeps the app's rail unless `fillsWindow` is set; then it fills the window without the rail (on phones the top bar stays above it, as above every page). `pluginRoutePath(id, path)` gives a page's path, and `usePluginRouteHref(id, path)` its `href` with the base path the app is served under, or after `#` with the hash router. An address `/p/<id>/...` that no page of an enabled plugin takes shows "Page not found" with the rail, where it is: no redirect, and no space or room named after its segments.
- A plugin's `public/` directory, if it has one, ships as it is: the build copies its files to `public/plugins/<id>/` of the app, and the dev server serves them there. That is for what the plugin does not import but loads by URL, such as a page for a frame, an image, a worker script or a font; `pluginPublicUrl(id)` is that directory's URL under the app's base path, such as `${pluginPublicUrl('my-plugin')}logo.svg` for `public/logo.svg`. Each plugin gets its own directory, and deployments serve it as the app's other files under `public/`: with the same headers, and a missing file is a 404, never the app. The build copies only files and directories: a symbolic link in `public/`, which could lead out of the plugin's directory, fails it, naming the link.
- Conversation covers (`src/app/plugins/conversationCovers.ts`) are the sixth kind: `{ covers, subscribe, Component, close? }`, a layer over a room's conversation while the room stays open, such as a full view of something the room works on. `covers(room)` says whether it covers the room's conversation now, and `subscribe(room, onChange)` calls `onChange` whenever that may change and returns its stop, as React's `useSyncExternalStore` takes them. `src/app/room/ConversationCover.tsx` shows the first, in build order, whose `covers` holds, with `Component` given the room, over the conversation column under the header and its slot. The host's rules apply on their own while it shows: the conversation under it is inert (no focus, clicks or find-in-page) and hidden from assistive technology, no read receipt goes out for it (`useReaderSees`, the Escape read), a message that arrives notifies and chimes as for a room not on screen, the composer sends no typing notice and stops one already out, its popovers (emoji board, autocomplete, model picker, menu) close, and a dropped file is not attached; the focus moves into the cover as it shows, Tab and Shift+Tab go round inside it, and the focus goes back where it was when it goes, and coming back reads what the reader then sees, as coming back to the window does. Escape in the cover calls `close(room)` when the plugin gives one, unless something in the cover took the key or an input method is composing. A cover that throws, in `covers`, `subscribe` or the stop it returns, `close` or `Component`, is taken away for that room, the next cover whose `covers` holds shows instead, and the failure is logged and reported with `[plugin <id>@<version>]`.
- Slash commands (`src/app/plugins/slashCommands.ts`) are the seventh kind: `{ name, description, run }`. The composer offers them after its own commands, in the same command menu, and runs them as it runs its own commands that act (`src/app/composer/commands/useCommands.ts`): the message is not sent, and `run({ room, args, threadId })` gets the room (matrix-js-sdk's `Room`, whose `client` is the account's client), the text typed after the name, and `threadId`, the root of the thread whose composer it was typed in (none in the main timeline or in Classic). In a thread whose root the server has not confirmed yet, the command waits, its text in the composer, until the root has its own ID, as a message sent there does. `name` is what follows the `/`, letters a to z only; `description` is a key of the plugin's strings, shown in the app's language in the menu. A built-in command keeps its name, also one a later version of the app adds, so a plugin's command of the same name is none, and a name claimed more than once, by one plugin or by several, runs for none of them, with one warning that names the plugins. A `run` that throws, or whose promise rejects, leaves the text in the composer with "/<name> failed: <the error's message>" above it, as a built-in command's failure does. One that throws `commandUsage()` from `core`, for a text after the name that it does not take, shows instead the usage line a built-in command shows, "Could not run /<name>. <its description>", in the app's language; for a message of its own in the app's language, it throws an error whose message `getPluginTranslation(id)` translates.
- Room menu entries (`src/app/plugins/roomActions.ts`) are the eighth kind: `{ id, label, icon, shows?, critical?, run }`. Every room's menu lists them, a sidebar row's (its More Options button, a right-click or a long press) and the open room header's alike (`src/app/room/RoomActionsMenu.tsx`), in build order, in a group of their own after the menu's first group and before Remove from, Archive and Leave. An entry that deletes or removes something says `critical: true`: the menu draws it as it draws Leave and lists it after Leave, at the end of the menu's last group, in build order; the app reads anything but `true` or nothing there as no entry. `label` and `icon` are as a header action's. `shows(room)`, pure and synchronous, says whether this room's menu lists the entry, and without it every room's does; one that throws leaves out only its entry, logged with `[plugin <id>@<version>]`. Choosing the entry closes the menu and calls `run({ room, showDialog })` with the menu's room (matrix-js-sdk's `Room`), open or not, in the same click, before the menu has gone. `showDialog(dialog)` shows what `dialog(close)` returns where the menu opened, as the menu's own Invite and Jump to Time show theirs: it stays after the menu has closed, until the plugin calls `close`. The menu shows one dialog at a time, so a later `showDialog` takes the place of the dialog it shows then: a `run` that has to load something shows its dialog first and loads inside it. A dialog that throws is taken away, and the failure is logged and reported with `[plugin <id>@<version>]`. A `run` that throws, or whose promise rejects, is logged with the tag. A header action, by contrast, is one of the open room's header actions, in its row or its menu, and runs with the IDs of the open room and its open thread; a room menu entry acts on whichever room's menu it is chosen in, with no thread.
- `plugins.<id>.enabled: false` in `config.json` hides a plugin's contributions, and `?plugins=off` in the address hides every plugin's for one page load.

A plugin's tests (`*.test.ts` and `*.test.tsx` in its directory, outside `node_modules`) run with the app's unit tests while `MINDROOM_CLIENT_PLUGINS` lists the plugin (`vitest.config.ts`): with the app's setup files, the SDK's subpaths and automatic JSX, and, as in the build, the app's copies of the packages it shares with plugins, for the plugin's files and for the ES modules of the packages it installed (Vite loads those); a CommonJS package's `require` of a shared package still resolves in the plugin's directory, and a plugin's own `.css.ts` files, which load its own vanilla-extract outside the setup's file scope, need a mock.

`src/app/plugins/__fixtures__/example-plugin/` is a small plugin for the tests, with a contribution of each kind, its strings in English and German, an image in its `public/` directory that its banner shows, and a build module (`build.mjs`) whose transform writes the banner's words in place of a marker; it imports the app only through the SDK, and its own test (`index.test.tsx`) uses only the SDK, `testing` included, and runs in every unit test run.

## Two lanes of code

Every file belongs to one of two lanes. [`docs/provenance.md`](provenance.md) records how each came to be, and [`AGENTS.md`](../AGENTS.md) holds the rules for editing them.

- **Lane P (ported).** Files written by Bas Nijholt for the earlier MindRoom client and licensed under Apache-2.0 for this project. They are listed at the paths they were imported at in `docs/provenance/portable.tsv` (code), `portable-wave2.tsv` (other text files: native shells, locales, scripts) and `portable-wave3.tsv` (binary assets); `dropped.tsv` lists the ones deleted during the rewrite. Lane P files are edited like any other file, but never run through a formatter.
- **Lane C (clean).** Everything else, written new for this repository: the app shell, client setup and sync, room list, timeline, composer editor, settings, sign-in pages, and the seams. Lane C must pass `just strict` and the type-aware ESLint rules of `just lint`.
- **Seams.** Modules that Lane P files import but that were not ported, with an implementation of their own. `docs/provenance/seams.tsv` lists each one's import-time path and the names Lane P imported from it, and `seams-dropped.tsv` the ones deleted or merged during the rewrite. A seam may move, be renamed or be merged like other Lane C code; the Lane P imports of it are re-pointed with it. When a Lane P test and a seam disagree, the seam changes.

`docs/provenance/moves.tsv` (old path, new path, batch) maps the files moved during the rewrite to their paths then, and `scripts/provenance-paths.cjs` folds it for the tools that sort files by lane (`strict-check.mjs`, the ESLint config, `similarity-audit.sh`, `check_holes.py`). These records are no longer kept up to date, so a Lane P file moved after the rewrite is Lane C to these tools: `just strict` and `just lint` hold it to Lane C's rules. To see which lane the tools give a file:

```bash
node scripts/provenance-paths.cjs lane src/app/matrix/protocol/toolTrace.ts src/app/config/useClientConfig.ts
node scripts/provenance-paths.cjs lane-p        # every Lane P file, at its path after the rewrite
```

`just check` enforces the split: `check-holes` proves each Lane P file differed from its import only in its blanked lines at the commit that filled them, `verify-ported` recomputes the import from a source checkout, and the overlap check described in `docs/provenance.md` runs over new code.

## MindRoom event formats

The MindRoom backend defines the formats its agents send, and the client reads them unchanged. The parsing and rendering are mostly Lane P code. The Lane C side supplies Matrix data and hands events over: the room view seams (`src/app/room/Room.tsx`, `src/app/timeline/RoomTimeline.tsx`), the message row seam (`src/app/timeline/message-rendering/useTimelineMessageFeature.tsx`), and `src/app/messages/content/RenderMessageContent.tsx`, which passes each message to `renderAgentMessageContent.tsx` first, unless a client plugin's renderer takes it ([Client plugins](#client-plugins)). Section 5 of `docs/baspowers/specs/2026-11-02-clean-room-client-design.md` gives the backend source for each format.

| Format | Shape | Read in (under `src/app/`) |
|---|---|---|
| Stream status | `io.mindroom.stream_status` (`pending`, `streaming`, `approval_pending`, `completed`, `cancelled`, `interrupted`, `error`) at the top of the reply's edits and in their `m.new_content` | `matrix/protocol/aiRun.ts`, `event-store/threads/useThreadStreamingState.ts`; a card streams only for a reply seen through /sync since its room's last gap or confirmed by the server (`matrix/client/streamingReplies.ts`; a thread list read confirms the replies it lists, and a room's checks wait for it, except while the read waits to ask for a failed page again: `event-store/threads/threadListRetry.ts`) |
| Live reply frames | `io.mindroom.live` ephemeral events that carry a reply while it streams, where the homeserver relays them | `messages/live/` |
| Tool trace | `io.mindroom.tool_trace`: `{version, events: [{type, tool_name, args_preview?, result_preview?, truncated?}], content_truncated?}` | `matrix/protocol/toolTrace.ts`, rendered by `messages/html/HtmlBlocks.tsx` |
| Run metadata | `io.mindroom.ai_run`: `{version, run_id, session_id, status, model, usage?}` | `matrix/protocol/aiRun.ts`, `event-store/threads/threadConversationCost.ts`; shown by `messages/MessageControls.tsx` |
| Thread title | an `m.notice` in the thread with `io.mindroom.thread_summary: {version, summary, generated_at, model, pinned}` | `matrix/protocol/threadSummary.ts`, `event-store/threads/threadSummaryTimeline.ts` |
| Conversation notice | an `m.notice` outside a thread with `io.mindroom.conversation: true` in its content and in the `m.new_content` of its edits, such as a card or a report that starts a conversation; the thread lists show it before anyone replies when a MindRoom agent on the active account's homeserver sent it, while any other notice but a call's row lists only once its thread has replies, and until then leaves a room with a MindRoom agent read | `matrix/protocol/conversationNotice.ts`, used by `event-store/threads/compactThreadRootData.ts` and `matrix/mainTimelineRead.ts` |
| Thread tags | room state `com.mindroom.thread.tags`, state key `["<root event ID>","<tag>"]`, content `{set_by, set_at, note?, data?}`; the tag `resolved` marks a resolved thread; `set_by` counts when the sender is that person or a MindRoom agent on the active account's homeserver, and a tag from anyone else names its sender | `event-store/threads/threadTags.ts`, `threads/tags/useMutateThreadTags.ts`, `threads/tags/useRoomThreadTags.ts` |
| Tool approval | event `io.mindroom.tool_approval` (`tool_name`, `arguments`, `status`, `approval_id`, `expires_at`, ...), answered with `io.mindroom.tool_approval_response` | `matrix/protocol/toolApproval.ts`, `approvals/approvalActions.ts`, `approvals/ToolApprovalCard.tsx` |
| Canvas page API | pages get `window.mindroom.submit`, `saveState`, `state` and `colorScheme`, and the `--mr-*` theme variables, in a sandboxed `srcdoc` frame with its own content security policy | `messages/canvas/canvasDocument.ts` |
| Computer | `/api/computers/*` on the MindRoom backend, a WebSocket for the screen, authorized with a Matrix OpenID token | `computer/api.ts` |
| MindRoom server | room state `io.mindroom.server`, keyed by each agent's user ID: `{api_origin, computer}` | `computer/agentServer.ts`, `computer/useAgentServers.ts`, `computer/useRoomMindroomServer.ts` |
| Client sessions | `POST /api/client-sessions` with a Matrix OpenID token bound to the server's origin for `{session_token, expires_at}`, sent as bearer to call transcripts and plugin routes and offered by websockets as `mindroom-session.<token>`; `DELETE /api/client-sessions` at sign-out | `computer/clientSessions.ts` |
| Call transcription | `/api/call-transcripts/v1/*` on the room's MindRoom server (the one its agents published while the homeserver binds OpenID tokens to it, else the deployment's; never this device's choice of server for computers) with a client session from a Matrix OpenID token; the router's call row, a notice with `io.mindroom.call: {call_id}` that it edits when the call ends (`ended_at`, `duration_seconds`) and again once the transcript message is posted (`transcript_event_id`); the transcript message in the row's thread, the notes as its body with `io.mindroom.call_transcript` and `io.mindroom.call_notes: {call_id}` | `calls/transcription/` (`api.ts`, `CallRow.tsx`), `matrix/protocol/callRow.ts`, `messages/content/CallTranscriptCard.tsx` |
| UI actions | `io.mindroom.ui_action` in an agent's message: show the computer or a canvas, open a panel or a Settings section | `matrix/protocol/chatUiProtocol.ts` |

Agents are recognized by their Matrix user ID (`mindroom_` localpart prefix, `matrix/protocol/agentIdentity.ts`). Other MindRoom data the client reads: `io.mindroom.settings` account data (`preferences/accountSettings.ts`), the router's `io.mindroom.auto_approve` room state (`approvals/auto-approve/`), and each agent's `io.mindroom.background_jobs` room state (`background-jobs/`).

The client's own account data: `io.mindroom.spaces` holds the rail's folders and saved space order (`src/app/spaces/sidebarSpaces.ts`), and `io.mindroom.room_order` the rooms a person dragged into their own order, per Rooms section: `{"lists": {"home": [<room ID>, ...], <space ID>: [...]}}`, where `home` is Home's section and a space's room ID is that space's (`src/app/sidebar/room-nav/roomOrder.ts`). A section without a list shows its rooms A to Z; rooms the list does not name follow the ones it does, A to Z, and Sort Rooms A to Z in the section's options menu deletes its list. `io.mindroom.client.settings` holds the app settings that follow the account, under their names in the device's `settings` entry: `{"version": 1, "isMarkdown": false, "hour24Clock": true, ...}` (`src/app/preferences/roamingSettings.ts`; the binding, with the edits not sent yet, is `src/app/matrix/hooks/useBindRoamingSettings.ts`).

Sub-rooms follow the backend's rule for rooms listed under a room: a chat room lists a room with `m.space.child` (non-empty `via`), and the listed room names it back as its canonical `m.space.parent`; MindRoom's agents in the chat room join such a room and leave it when it is taken off the list. The parent map (`matrix/state/roomToParents.ts`) records a joined room, other than a Space, as a sub-room only while both links hold, and a listed room the user has not joined on the listing alone, as it records the Spaces' children, so a sub-room counts as part of the Spaces above its room. Home and a Space show each sub-room under its room, and the rooms the chat room lists that the user has not joined, which open their preview to join (`sidebar/room-nav/SubRoomRows.tsx`). The room menu's New Sub-room (`rooms/create/CreateSubRoomDialog.tsx`) makes a `restricted` room that only the chat room's members may join, and Remove from takes a sub-room off its chat room's list (an empty `m.space.child`) and leaves the sub-room's own link, which the agents read to leave it. A room upgrade (`rooms/settings/general/moveSpaceLinks.ts`) lists the old room's children in the new room and moves the link of each sub-room the account may change to the new room, and such a `restricted` sub-room that admitted the old room's members admits the new room's too; the room settings name the sub-rooms that did not come along.

Two tests pin formats to what the backend actually sends: `src/app/messages/backendApprovalContract.test.ts` reads approval events captured from the backend (`src/app/messages/__fixtures__/backendApprovalContract.json`), and `src/app/messages/__fixtures__/backendToolMarkerBodies.json` holds the backend's own HTML for tool markers, written by `scripts/capture-backend-tool-marker-bodies.py`. The backend's `docs/streaming.md`, `docs/canvases.md` and `docs/tools/worker-computer.md` describe the formats in prose.
